01

The trade-off nobody writes down

Dispatch software usually optimises one thing. Drivers live with two.

Sort purely by urgency and the van zig-zags across the city, burning fuel and time to honour an order that a customer never sees. Sort purely by geography and the insulin sits in the back until stop eleven.

The planner treats these as separate stages rather than one impossible score. Urgency decides who is in today's batch and in what tier. The route optimiser then decides how to physically cover that batch. Neither stage has to pretend the other doesn't exist.

02

How a run happens

  1. 01

    Intake

    Packages arrive with coordinates and a priority flag. Nothing is assumed to be sorted — real queues arrive half-ordered, which is exactly where naive pivots fall over.

  2. 02

    Sort

    Quicksort orders the queue by urgency using a middle-element pivot, so a partially sorted input doesn't collapse the partition into O(n²).

  3. 03

    Evolve

    A population of candidate routes is scored by total distance. The best survive, swap segments, and mutate. After 80 generations the improvement curve has usually flattened.

  4. 04

    Dispatch

    The winning permutation is returned as a stop list with its distance, so it can be compared against the raw priority order.

03

The two algorithms, and why those two

Sorting

Quicksort, middle pivot

in-place · unstable · Θ(n log n) average

Urgency has few distinct values, so the interesting failure isn't speed on random data — it's what happens when yesterday's list comes back nearly sorted. Taking the first or last element as the pivot on that input produces maximally unbalanced partitions and quadratic behaviour.

Picking the middle element costs nothing and removes the common case of that failure. Merge sort would guarantee the bound, but it needs O(n) extra space for a queue that is already in memory and doesn't need stability here.

pivot = arr[len(arr) // 2]
left  = [x for x in arr if x.priority < pivot.priority]
mid   = [x for x in arr if x.priority == pivot.priority]
right = [x for x in arr if x.priority > pivot.priority]
return quicksort(left) + mid + quicksort(right)

Routing

Genetic algorithm over the TSP

heuristic · no optimality guarantee

Visiting every stop once at minimum distance is the Travelling Salesman Problem. Exhaustive search is O(n!) — twelve stops is already 479 million orderings, and a depot is rarely that small.

So the planner stops asking for the best route and asks for a good one, quickly. Each candidate is a permutation of stops; fitness is the inverse of total distance; strong routes are kept, recombined, and occasionally mutated by swapping two stops. It's a hill climb with enough randomness to avoid the first hill it finds.

A genetic algorithm will not return the optimal tour, and it won't return the same tour twice. For dispatch planning, a route within a few percent of optimal in under a second beats an exact answer nobody waits for.

04

Complexity

Operation Best Average Worst Space
Quicksort by urgency Ω(n log n) Θ(n log n) O(n²) O(log n)
Route distance evaluation Ω(n) Θ(n) O(n) O(1)
Genetic algorithm (g generations, p population) Θ(g · p · n) per run O(p · n)
Exact TSP by brute force (not used) Θ(n!) O(n)

Runtime is bounded by the generation count rather than by the number of stops, which is what makes the planner predictable to run — and what caps how good its answer can get.

05

What it doesn't do yet

  • Distance is Euclidean. Straight lines between coordinates, not road distance. Real streets, one-ways and traffic would change the ranking of routes.
  • One vehicle, unlimited capacity. Splitting a batch across vans is a different problem (vehicle routing) and needs a different fitness function.
  • No time windows. A delivery that must land between 09:00 and 11:00 is currently just another priority tier.
  • Fixed generation count. Stopping at 80 rather than when improvement stalls wastes work on easy batches and cuts hard ones short.
